# Требования к веб-приложению Task Manager

Статус: v1.0 — согласовано, готово к этапу планирования

## 1. Назначение и контекст

Приложение для систематизации и учёта задач пользователя по нескольким направлениям жизни:
- несколько работ (2+ проекта/работодателя),
- учёба,
- поиск работы (отклики, собеседования, дедлайны).

Главная ценность: видеть всё в одном месте, не пропускать сроки, понимать загрузку.

## 2. Предметная область (сущности)

- **Направление (Sphere/Area)** — верхний уровень: «Работа А», «Работа Б», «Учёба», «Поиск работы». У каждого свой цвет.
- **Проект** — группировка задач внутри направления (например, «Диплом» в «Учёбе»).
- **Задача** — название, описание, статус, приоритет, дедлайн, оценка времени, теги.
- **Подзадачи / чек-лист** — внутри задачи.
- **Повторяющиеся задачи** — ежедневно/еженедельно/по расписанию.
- **Учёт времени (time entry)** — фактические затраты времени по задаче (таймер или ручной ввод).
- **Уведомление** — напоминание о дедлайне или о запланированном времени.

## 3. Функциональные требования

### 3.0. Пользователи и доступ
- FR-0.1. Регистрация и вход по email + пароль (несколько пользователей, у каждого свои данные).
- FR-0.2. Сессии/токены, выход из аккаунта, смена пароля.
- FR-0.3. Совместная работа (шеринг проектов) — **не входит в MVP**, но модель данных не должна мешать добавить позже.

### 3.1. Задачи
- FR-1. Создание/редактирование/удаление задач с полями: название, описание, направление, проект, приоритет, дедлайн, теги, оценка времени.
- FR-2. Статусы задач: backlog → to do → in progress → done (+ отменено).
- FR-3. Подзадачи (чек-лист) внутри задачи.
- FR-4. Повторяющиеся задачи с настраиваемым расписанием.
- FR-5. Быстрое добавление задачи (quick add) одной строкой.
- FR-6. Перетаскивание задач между статусами/датами (drag & drop).

### 3.2. Представления
- FR-7. Список задач с фильтрами (направление, проект, статус, приоритет, тег, срок) и поиском.
- FR-8. Kanban-доска по статусам.
- FR-9. Календарь (неделя/месяц) с задачами по дедлайнам.
- FR-10. Вид «Сегодня»: что запланировано и что просрочено, по всем направлениям.
- FR-11. Вид по направлению: все задачи конкретной работы/учёбы/поиска работы.

### 3.3. Сроки и уведомления
- FR-12. Дедлайны с датой и опционально временем.
- FR-13. Напоминания: за N минут/часов/дней до дедлайна (настраивается на задачу).
- FR-14. Push-уведомления в браузере через Web Push, работают при закрытой вкладке (сервер + service worker + подписка на устройстве).
- FR-15. Индикация просроченных задач (подсветка + отдельный фильтр).
- FR-16. Ежедневная сводка «план на день» (уведомление утром) — опционально.

### 3.4. Таймеры и учёт времени
- FR-17. Таймер (start/stop) на задаче; одновременно активен только один таймер.
- FR-18. Ручное добавление времени к задаче.
- FR-19. Сравнение «оценка vs факт» по задаче.
- FR-20. Отчёт по времени: сколько часов за день/неделю/месяц по направлениям и проектам (диаграмма + таблица).

### 3.5. Прочее
- FR-21. Тёмная/светлая тема.
- FR-22. Экспорт данных (JSON/CSV) и отчётов по времени (CSV).
- FR-23. «Поиск работы» — обычный проект с задачами и статусами, без отдельной сущности/воронки. Кастомные статусы не нужны.

## 4. Нефункциональные требования

- NFR-1. Веб-приложение, адаптивная вёрстка (desktop-first, пригодно на планшете/телефоне).
- NFR-2. Быстрый отклик UI (<100 мс на типовые операции). Офлайн-режим и PWA не требуются — приложение работает только онлайн, но должен быть service worker для Web Push.
- NFR-3. Данные сохраняются надёжно, автосохранение при редактировании.
- NFR-4. Локализация: русский язык интерфейса (архитектурно — с возможностью добавить другие).
- NFR-5. Развёртывание: локально / self-hosted через docker-compose; архитектура должна позволять перенос в облако без переписывания.
- NFR-6. Web Push требует HTTPS на проде; для локальной разработки допустимо localhost (исключение из HTTPS-требования браузеров).
- NFR-7. Интеграции с внешними сервисами (Google Calendar и т.п.) в MVP не входят, но архитектура должна иметь точку расширения (например, отдельный модуль/сервис синхронизации и webhooks).

## 5. Принятые решения (по итогам уточнений)

1. Пользователи: несколько, у каждого свои данные. Авторизация — email + пароль, без OAuth и 2FA.
2. Хостинг: сначала локально / self-hosted (docker-compose), с возможностью переезда в облако.
3. Уведомления: Web Push при закрытой вкладке (сервер + service worker).
4. «Поиск работы»: обычный проект, без отдельной воронки и кастомных статусов.
5. Offline/PWA: не нужно.
6. Интеграции: не в MVP, заложить точку расширения.
7. Стек: предпочтений нет — выбрать на этапе планирования.

## 6. Что НЕ входит в MVP (out of scope)

- Совместная работа, шеринг проектов, комментарии, @упоминания.
- Интеграции с внешними календарями и сервисами.
- Офлайн-режим, нативные мобильные приложения.
- OAuth, 2FA, SSO.
- Кастомные статусы задач и воронки.
