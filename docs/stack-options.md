# Варианты технологического стека

Статус: выбран вариант A (Next.js fullstack) — зафиксировано в `docs/plan.md`

Общие для всех вариантов компоненты:

- **БД:** PostgreSQL — реляционная модель (пользователи, проекты, задачи, time entries), надёжная, стандарт для self-hosted.
- **Планировщик напоминаний:** фоновый worker, который проверяет дедлайны и шлёт Web Push (отдельный контейнер в docker-compose).
- **Web Push:** библиотека `web-push` (Node) / `pywebpush` (Python), VAPID-ключи; service worker на фронтенде.
- **Развёртывание:** docker-compose (app + worker + postgres).

---

## Вариант A. Next.js (fullstack TypeScript) — РЕКОМЕНДУЕМЫЙ

**Стек:** Next.js (App Router) + React + TypeScript + Prisma + PostgreSQL + отдельный worker (Node) для пушей.

**Плюсы:**

- Один язык (TypeScript) и один репозиторий-проект на всё: UI, API (route handlers), типы общие между фронтом и бэком.
- Минимум инфраструктуры: один контейнер приложения + worker + БД. Самый простой docker-compose.
- SSR/SSR-гидратация из коробки — быстрая первая загрузка.
- Огромная экосистема React: kanban (dnd-kit), календарь, графики (Recharts).
- Легко переехать в облако (Vercel, любой VPS, Docker).

**Минусы:**

- Планировщик пушей — отдельный процесс, который надо написать и поддерживать (небольшой, ~100 строк, но всё же).
- Next.js навязывает свои соглашения; App Router местами нетривиален.
- Серверная логика «размазана» по route handlers — для дисциплины нужно сразу выделить слой сервисов.

**Кому подходит:** хотим быстро получить работающее приложение с минимумом движущихся частей.

## Вариант B. NestJS + React (раздельные бэкенд и фронтенд)

**Стек:** NestJS (TypeScript) + PostgreSQL (TypeORM/Prisma) + React (Vite) SPA.

**Плюсы:**

- Чёткая архитектура бэкенда: модули, сервисы, DI — хорошо растёт, если приложение будет развиваться.
- Встроенные средства для фоновых задач (@nestjs/schedule, BullMQ) — планировщик напоминаний «из коробки».
- REST API сразу оформлен как отдельный контракт — легко добавить мобильный клиент или интеграции потом.
- TypeScript на обоих концах.

**Минусы:**

- Два приложения = два контейнера + CORS + проксирование, сложнее docker-compose и разработка.
- Больше « boilerplate»: DTO, модули, декораторы — медленнее старт.
- Нет SSR (для внутреннего приложения не критично).

**Кому подходит:** планируем долгую жизнь проекта, ценим строгую архитектуру бэкенда.

## Вариант C. FastAPI + React

**Стек:** Python (FastAPI) + PostgreSQL (SQLAlchemy) + React (Vite) SPA + Celery/APScheduler для пушей.

**Плюсы:**

- FastAPI — очень быстрая разработка API, автоматическая OpenAPI-документация.
- Python удобен для отчётов/аналитики по времени (pandas при желании).
- Pydantic — строгая валидация данных.

**Минусы:**

- Два языка (Python + TypeScript) — переключение контекста, дублирование моделей.
- Те же минусы раздельной архитектуры, что у варианта B.
- Celery тянет Redis — лишний контейнер (можно обойтись APScheduler, но это менее стандартно).

**Кому подходит:** если бэкенд хочется писать на Python.

---

## Вариант D. Django (без SPA, server-side rendering + HTMX/Alpine)

**Стек:** Django + PostgreSQL + шаблоны + HTMX для динамики + django-celery-beat для пушей.

**Плюсы:**

- Максимум «из коробки»: админка, auth (email+пароль), ORM, миграции, сессии.
- Минимум JavaScript — быстрее всего писать CRUD и отчёты.
- Один язык, один процесс, самый простой деплой.

**Минусы:**

- Kanban с drag & drop, календарь, таймер в реальном времени — это интерактивный UI; на HTMX делать заметно тяжелее, чем на React. Придётся встраивать JS-островки, и граница «штаты/островки» будет мешать.
- Web Push + service worker всё равно требуют JS на клиенте.
- UI будет ощущаться менее «приложением» и более «сайтом».

**Кому подходит:** если интерактивность UI не важна. Для нашего ТЗ (канбан, драг, таймеры) — слабый вариант.

## Сравнение по критериям ТЗ

| Критерий                          | A. Next.js   | B. NestJS+React | C. FastAPI+React | D. Django                |
| --------------------------------- | ------------ | --------------- | ---------------- | ------------------------ |
| Скорость разработки MVP           | высокая      | средняя         | средняя          | высокая (но страдает UI) |
| Интерактивный UI (канбан, таймер) | отлично      | отлично         | отлично          | слабо                    |
| Web Push + планировщик            | свой worker  | из коробки      | Celery/Redis     | Celery/Redis             |
| Простота docker-compose           | 3 контейнера | 4 контейнера    | 4–5 контейнеров  | 3–4 контейнера           |
| Один язык                         | да           | да              | нет              | да (почти)               |
| Рост после MVP (интеграции, API)  | хорошо       | отлично         | отлично          | хорошо                   |
| Переезд в облако                  | проще всех   | просто          | просто           | просто                   |

## Рекомендация

**Вариант A (Next.js)** — оптимален для MVP: минимум инфраструктуры, один язык, весь интерактивный UI на React, легко развернуть и легко перенести. Единственная «ручная» часть — worker для пушей, что компенсируется его простотой.

**Вариант B (NestJS + React)** — выбрать, если проект задуман как долгоживущий с большим бэкендом, и готовы платить за это более сложной инфраструктурой.

Варианты C и D — если есть привязка к Python; для нашего ТЗ объективных преимуществ не дают.
