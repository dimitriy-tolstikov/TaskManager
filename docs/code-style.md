# Code Style и архитектурные правила

Статус: v1.0 — согласовано

Стек: Next.js (App Router) + TypeScript + Prisma + Tailwind + shadcn/ui.

Принципы сверху вниз: **KISS → читаемость → DRY → SOLID**. Если правило конфликтует с простотой — побеждает простота.

## 1. Главные принципы

- **KISS.** Решаем задачу самым простым способом, который работает. Никаких абстракций «на будущее»: три похожих фрагмента кода лучше, чем преждевременная абстракция. Абстракция появляется только когда есть 3+ реальных случая использования.
- **DRY, но не догматично.** Дублирование устраняем, когда оно уже появилось (правило трёх), а не когда «вдруг понадобится».
- **SOLID — прагматично.** В первую очередь: единственная ответственность (один модуль/компонент — одна причина для изменения) и явные зависимости (всё через параметры/импорты, никаких скрытых глобалей). Интерфейсы и инверсия зависимостей — только там, где есть реальная сменяемость (например, отправитель уведомлений: Web Push сейчас, Telegram потом).
- **YAGNI.** Не пишем код, который не требуется текущей итерацией плана.

## 2. Декомпозиция и размеры (жёсткие лимиты)

| Артефакт            | Лимит                              | Что делать при превышении                      |
| ------------------- | ---------------------------------- | ---------------------------------------------- |
| Функция             | ≤ 30 строк, ≤ 3 уровня вложенности | выделить подфункции с говорящими именами       |
| React-компонент     | ≤ 100 строк (файл ≤ 200)           | разбить на подкомпоненты, вынести логику в хук |
| Файл                | ≤ 300 строк                        | разбить на модули                              |
| Route handler (API) | ≤ 30 строк                         | тонкий контроллер: валидация → сервис → ответ  |
| Сервисный метод     | ≤ 50 строк                         | декомпозировать по шагам сценария              |

Если файл/компонент растёт — это сигнал декомпозировать, а не «дописать ещё немного».

Лимиты закреплены как **ESLint-ошибки** (`max-lines`, `max-lines-per-function`, `max-depth` в eslint.config с настройкой exclude для тестов и миграций). Сборка падает при превышении — исключения только через осознанный `// eslint-disable-next-line` с комментарием-причиной.

**Компоненты:**

- Один компонент — один файл, имя файла = имя компонента (`TaskCard.tsx`).
- Компонент либо **отображает данные** (presentational), либо **управляет состоянием/загрузкой** (container). Смешивание — только для мелких компонентов.
- Логика, не привязанная к рендеру (вычисления, фильтрация, форматирование), выносится в чистые функции в `lib/` — их легко тестировать.
- Повторяющаяся логика состояния — в кастомные хуки (`useTaskTimer.ts`).

**Пропсы:** ≤ 5 пропсов — объект params дальше не нужен; больше — группировать в объект или пересматривать декомпозицию. Никакого prop drilling глубже 2 уровней — тогда React Context или поднятие состояния.

## 3. Слоистость (backend)

```
route handler (app/api/...)  →  сервис (lib/services/...)  →  Prisma
        ↓                            ↓
   zod-валидация,              бизнес-правила,
   HTTP-коды                   транзакции, побочки
```

- Route handlers **не содержат** бизнес-логики и SQL/Prisma-вызовов.
- Сервисы **не знают** про HTTP (никаких `NextRequest`/`NextResponse` внутри) — принимают типизированные аргументы, возвращают данные или кидают доменные ошибки.
- Прямой доступ к Prisma — только из сервисов (и worker'а).
- Zod-схемы — единый источник правды: одна схема используется и в форме (react-hook-form), и в API-валидации.

## 4. TypeScript

- `strict: true`, без `any` (eslint-правило `no-explicit-any: error`). Неизвестное — `unknown` + сужение типа.
- Типы БД — из Prisma (`Task`, `User`...), не дублируем вручную.
- Для API-границ — типы, выведенные из zod-схем (`z.infer`).
- Не экспортируем типы «про запас»: тип живёт рядом с тем, что типизирует.
- `enum` статусов/приоритетов — из Prisma schema, не разъезжаемся.

## 5. Именование

- Файлы компонентов — `PascalCase.tsx`, всё остальное — `camelCase.ts` (`taskService.ts`, `useTaskTimer.ts`).
- Переменные/функции — `camelCase`, типы — `PascalCase`, константы — `SCREAMING_SNAKE` только для настоящих констант конфигурации.
- Булевы — с префиксом: `isDone`, `hasDeadline`, `canEdit`.
- Обработчики событий: `handle*` в компоненте (`handleSubmit`), `on*` в пропсах (`onSubmit`).
- Имена — длинные и понятные вместо коротких и загадочных: `overdueTasks`, не `ot`.

## 6. Импорты и организация файлов

- Порядок импортов (eslint `import/order`): внешние → алиасы `@/` → относительные; группы разделены пустой строкой.
- Алиас `@/*` → корень проекта; относительные импорты только внутри одной папки (`./TaskCard`).
- **Без barrel-файлов** (`index.ts` с реэкспортами) — они мешают tree-shaking и навигации. Исключение: `components/ui/` от shadcn (там это конвенция).
- Колокация: компонент, его стили-тесты-подкомпоненты — в одной папке (`TaskCard/`), пока папка не разрослась.

## 7. Обработка ошибок

- Доменные ошибки — классы в `lib/errors.ts` (`NotFoundError`, `ValidationError`, `ConflictError`); сервисы кидают их, route handler маппит в HTTP-коды в одном месте.
- Нет пустых `catch {}` и `catch` с одним `console.log`.
- Пользовательские ошибки (валидация) — понятные сообщения на русском; системные — логируем, наружу отдаём общее «Что-то пошло не так».
- На клиенте — error boundary на уровне маршрута (стандартный `error.tsx` Next.js).

## 8. React / Next.js специфика

- Server Components по умолчанию; `'use client'` — только там, где есть интерактив (состояние, эффекты, браузерные API). Клиентский компонент — как можно ниже по дереву.
- Состояние: локальное (`useState`) → поднятое → Context → внешний стор. Zustand/Redux не вводим, пока Context не перестанет справляться (ожидаемо — не введём вообще).
- Серверные данные — через fetch в RSC или route handlers + `useSWR`/react-query **только если** появится реальная потребность в кэше/ревалидации на клиенте (пока — нет).
- `useEffect` — только для синхронизации с внешним миром (таймер, подписки). Производные данные — `useMemo` или просто вычисление в рендере.
- Списки — всегда со стабильным `key` (id сущности, не индекс).

## 9. CSS / стили

- Tailwind utility-классы прямо в разметке; при повторе 3+ раз одного набора классов — выделить компонент (не `@apply`).
- Кастомный CSS — только там, где Tailwind не выражает (сложные анимации); файл рядом с компонентом.
- Цвета/отступы — из темы (CSS-переменные shadcn), никаких магических hex в разметке.

## 10. Комментарии

- Код объясняет себя сам; комментарий — только для «почему», не «что» (почему такое решение, обход бага, ссылка на issue).
- TODO/FIXME — только с описанием условия, когда это будет сделано.
- Язык комментариев: **английский** (стандарт индустрии, код читабелен вне контекста проекта).
- JSDoc — только для публичных функций сервисов с неочевидным контрактом.

## 11. Тесты

- Тестируем сервисы и чистые функции (Vitest), а не компоненты поголовно. Критичная логика (повторения, напоминания, учёт времени, auth) — покрыта обязательно.
- Один e2e-smoke (Playwright) на ключевой сценарий, без попытки покрыть всё.
- Тесты — такие же простые, как код: arrange/act/assert, без сложных фабрик.

## 12. Инструментальное закрепление

- ESLint (next/core-web-vitals + typescript + import/order + no-explicit-any + лимиты размеров) — ошибки, не warnings.
- Prettier — форматирование на сохранение, конфликты с ESLint отключены.
- pre-commit: `lint-staged` (eslint + prettier на изменённые файлы) + `tsc --noEmit`.
- CI позже; локальный pre-commit обязателен с M0.

## 13. Git-процесс

- **Ветки:** feature-ветка на итерацию/фичу (`feat/m1-tasks-core`, `fix/timer-reset`), merge в `main` после проверки. Прямые коммиты в `main` не делаем.
- **Коммиты:** Conventional Commits на английском — `feat:`, `fix:`, `refactor:`, `test:`, `chore:`, `docs:` (например, `feat: add task quick add`). Один коммит — одно логическое изменение.
- Перед merge в `main`: сборка зелёная, тесты итерации проходят, чек-лист итерации выполнен.
